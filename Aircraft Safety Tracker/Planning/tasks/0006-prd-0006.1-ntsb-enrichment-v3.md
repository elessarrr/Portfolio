## 1. Introduction/Overview

### Problem statement

The v3 app provides a strong ASN baseline (`Incident.asn_url`), but ASN does not contain every incident that appears in official sources. We want to **enrich** the dataset with **NTSB-only incidents** (Boeing/Airbus only), while keeping the product simple:

- ASN remains the primary baseline; existing incidents keep ASN `Details` links.
- NTSB is used only to **add new incidents** ASN did not capture (no link toggles, no multi-link UI).
- NTSB-only rows must look **identical** to ASN rows in the UI (same incident list; no badges or separate sections).

Two product risks drive this PRD:

1. **Duplication:** Naïve NTSB import would create double incidents (same event in ASN and NTSB).
2. **Dead links:** Many NTSB docket URLs resolve to *“The docket for this investigation has not been released”* — especially foreign-led accredited-rep cases (`*WA*`, `*RA*`, `cm_agency=Other`) and DirectorBrief records. We must not add incidents whose Details link is a dead end.

### Goal

Import NTSB records and **only create new `Incident` rows** when:

1. The record is **not** confidently matched to an existing ASN incident (dedupe pass), **and**
2. The resolved NTSB URL is **verified working** at import/audit time (link viability pass).

---

## 2. Goals

1. **Enrich coverage:** Add NTSB-only incidents (Boeing/Airbus) that ASN did not capture **and** that have working official links.
2. **Strong deduplication:** Prevent duplicates against ASN via a documented, testable score-based policy.
3. **Link quality gate:** Reject NTSB-only candidates whose Details URL lands on unreleased dockets or other known dead-end pages.
4. **Simple UI contract:** NTSB-only incidents appear as normal rows; no UI changes in this PRD.
5. **Audit before write:** Run full-corpus dedupe + link checks and produce a reviewable viable set **before** any DB writes.
6. **No regression:** Existing ASN pages and links continue working; test suite stays green.

---

## 3. User Stories

1. **As a** portfolio visitor browsing an aircraft model,  
   **I want** to see additional NTSB incidents that aren’t in ASN **and** have a working Details link,  
   **so that** the safety record feels more complete without dead-end clicks.

2. **As a** portfolio visitor,  
   **I want** the Details link for an NTSB-only incident to open a real NTSB page (CAROL or released docket),  
   **so that** I can verify the record.

3. **As a** product owner,  
   **I want** duplicates against ASN removed before import and broken NTSB links excluded,  
   **so that** users trust the dataset.

## 4. Functional Requirements

### FR-1: Scope (Boeing/Airbus only)

1. **FR-1.1** Ingest only NTSB records for **Boeing** or **Airbus** aircraft (consistent with v3 scope).
2. **FR-1.2** Skip non-Boeing/Airbus records; do not create `Incident` rows.

### FR-2: NTSB acquisition inputs (prototype)

1. **FR-2.1** Define one canonical on-disk input format (JSON list of NTSB records matching `NTSBImporter.parse()` contract).
2. **FR-2.2** Accept input path via CLI/ENV/config (e.g. `--input data/raw/ntsb_records.json`).
3. **FR-2.3** Support at least: manual file drop (default), optional download+cache stub, optional committed snapshot — document trade-offs.

**Prototype default:** Bootstrap from v2 `IncidentSource.source_data` export or manual file drop; do not block on choosing a live NTSB endpoint yet.

### FR-3: “NTSB-only incident” creation rule

1. **FR-3.1** For each NTSB record, attempt ASN dedupe match (see FR-4).
2. **FR-3.2** If ASN-covered above threshold, **do not** create a new `Incident` row.
3. **FR-3.3** If not ASN-covered **and** link viability passes (see FR-5), create a new `Incident` with minimum fields: date, aircraft model, operator, location, fatalities, description, incident_type.
4. **FR-3.4** If not ASN-covered but link is **not** viable, **do not** insert — note in audit report (broken/unreleased link).
5. **FR-3.5** NTSB-only incidents appear in the same incident list as ASN rows (no UI changes).

### FR-4: Deduplication policy (balanced, score-based)

1. **FR-4.1** Compute a dedupe score comparing each NTSB record to nearby ASN incidents for the same aircraft model (when resolvable).
2. **FR-4.2** Score signals: date ±1 day, location fuzzy, operator fuzzy, fatalities proximity.
3. **FR-4.3** Treat as ASN-covered when **≥ 2 strong signals** match (threshold codified in tests).
4. **FR-4.4** Dedupe logic must be deterministic with unit tests.
5. **FR-4.5** Emit dedupe audit report: counts + sample closest matches for skipped records.

### FR-5: Details link behavior + viability gate

1. **FR-5.1** Resolve URL via `resolve_ntsb_source_url()` (CAROL when public content + not Other/DirectorBrief; else docket; else brief).
2. **FR-5.2** **Link viability check (required before insert):** HTTP fetch resolved URL and reject if response indicates:
   - *“The docket for this investigation has not been released”*
   - Other known dead-end patterns (document as discovered)
3. **FR-5.3** Only NTSB-only candidates with **viable** URLs proceed to insert consideration.
4. **FR-5.4** Foreign-led (`cm_agency=Other`) and DirectorBrief records that resolve to unreleased dockets must be **excluded** from the viable set (not inserted with dead links).

### FR-6: Aircraft model resolution (audit phase)

1. **FR-6.1** For dedupe audit, if NTSB record is Boeing/Airbus but `Aircraft.model_name` is not found in v3 DB, **still include** the record in the viable-set pipeline (do not skip as `missing_aircraft` during full-corpus audit).
2. **FR-6.2** Dedupe against ASN may be limited when aircraft_id is unknown; document in report.
3. **FR-6.3** Before write-path import (later phase), define model normalization/create rules — out of scope for audit-only phase.

### FR-7: Full-corpus viability audit (new phase — before write)

1. **FR-7.1** Run dedupe + link check on the **full** NTSB input corpus (not just a 500-record sample).
2. **FR-7.2** Produce report buckets:
   - `total_parsed`
   - `skipped_not_boeing_airbus`
   - `skipped_deduped_asn_covered` (duplicates — removed from viable set)
   - `viable_unique` (not ASN-covered, Boeing/Airbus, included even if aircraft not in DB)
   - `viable_with_working_link`
   - `viable_with_broken_link` (excluded from insert)
3. **FR-7.3** Include sample rows (≥10) for each bucket for product review.
4. **FR-7.4** **Review gate:** Product approves viable set before any write-path import.

### FR-8: Data model constraints (v3-friendly)

1. **FR-8.1** ASN incidents continue using `Incident.asn_url`.
2. **FR-8.2** NTSB-only incidents store Details URL in `IncidentSource.source_url`; `link_picker` returns it when ASN is absent.
3. **FR-8.3** No multi-link UI or source toggles in this PRD.

### FR-9: Testing + QA

1. **FR-9.1** Unit tests: dedupe decisions, URL resolver, link viability detector (mock HTTP).
2. **FR-9.2** `PYTHONPATH=. pytest -q` stays green.
3. **FR-9.3** Manual smoke (post-write phase only): verify NTSB-only rows look like ASN rows and Details links work.

## 5. Non-Goals (Out of Scope)

1. No FAA (AIDS/SDR) ingestion.
2. No merging NTSB into existing ASN incidents.
3. No UI toggles, badges, or separate NTSB sections.
4. No family rollup/taxonomy work.
5. No production Railway backfill in this PRD.
6. No inserting incidents with unreleased/broken NTSB docket links.

---

## 6. Design Considerations

- NTSB-only incidents must be **visually identical** to ASN rows.
- Users should never click Details and land on “docket not released.”
- UI changes are **explicitly deferred** until link viability audit is approved.

## 7. Technical Considerations

### Pipeline (audit → review → write)

```text
NTSB JSON input
  → parse (Boeing/Airbus filter)
  → dedupe vs ASN (score-based; include unknown-aircraft rows)
  → remove ASN duplicates → viable unique set
  → resolve URL + viability check
  → split: working_link vs broken_link
  → audit report + samples
  → [REVIEW GATE — product approval]
  → write-path import (later phase)
```

### Known link failure patterns (from review 2026-05-28)

- Docket URL + `cm_agency=Other` → often unreleased docket page.
- Docket URL + `DirectorBrief` → often unreleased docket page.
- CAROL blocked for Other/DirectorBrief by design; docket fallback is frequently empty.
