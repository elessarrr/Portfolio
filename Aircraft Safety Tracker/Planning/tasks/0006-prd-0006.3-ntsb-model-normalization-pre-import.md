## 1. Introduction/Overview

### Problem statement

PRD 0006.2 completed the audit export and FR-12 link gate. Product signed off on **657 working-link** NTSB candidates. Import is still blocked:

| Issue | Current state | Risk if we import naïvely |
|-------|---------------|---------------------------|
| **Exact-string aircraft lookup** | **632/657** rows have `unknown_aircraft=true` | `resolve_boeing_airbus_aircraft_id()` **auto-creates** a new `Aircraft` row on every exact miss |
| **String fragmentation** | **279** distinct NTSB `make_model` strings in the 657-row set vs **97** rows in v3 catalog | ~250 thin aircraft pages (`BOEING A75N1(PT17)`, `Boeing 737-347`, etc.) |
| **Weaker ASN dedupe** | When `aircraft_id` is unknown, ASN dedupe is skipped (FR-6.2) | Residual duplicate incidents after import |
| **No post-import safety net** | Auto-create path has no canonical gate | Duplicate `Aircraft` rows that differ only by casing/spacing/variant suffix |

**Example:** NTSB row `DCA01MA065` has `make_model: "Boeing 757"` and `unknown_aircraft: true` — it is a real Boeing incident with a working docket, but no exact catalog match. Import today would create `Aircraft(model_name="Boeing 757")` instead of attaching to an existing 757 family page.

### Goal

Before Task 6.0 bulk import:

1. **Catalog** all NTSB `make_model` strings in the 657 working-link set.
2. **Propose and approve** a family rollup policy (variant-level pages where incident volume justifies it; roll up only where helpful).
3. **Build a canonical pre-import mapping** (JSONL) from NTSB strings → existing v3 `aircraft_id`.
4. **Harden dedupe** and **disable silent auto-create** during bulk import.
5. **Run a post-import duplicate audit** to catch anything the gate missed.

---

## 2. Goals

1. **Zero catalog bloat:** Bulk import must not create new `Aircraft` rows except where product explicitly approves (Stearman/helicopter families per rollup policy).
2. **User-useful granularity:** Keep variant-level aircraft pages when incident count is high enough to justify a standalone list (e.g. 747-100 with many incidents stays separate; do not force-roll into generic "Boeing 747" if that produces an unusably long mixed list — product sets threshold).
3. **Canonical gate:** Every imported NTSB row resolves `aircraft_id` via an approved mapping file — not ad-hoc auto-create.
4. **Stronger dedupe:** Re-run ASN dedupe using family-resolved `aircraft_id` where possible (recover dedupe for rows that were `unknown_aircraft=true` at audit time).
5. **Verifiable safety:** Post-import audit confirms no duplicate incidents (NTSB vs ASN) and no near-duplicate `Aircraft` rows.
6. **Schema confidence:** Confirm `Aircraft.model_name` length limit accommodates all approved canonical names (truncate only documented edge cases).

---

## 3. User Stories

1. **As a** portfolio visitor,  
   **I want** NTSB incidents grouped under the same aircraft pages I already browse (737-800, A320, etc.),  
   **so that** I don't land on empty or one-off model pages.

2. **As a** portfolio visitor browsing a high-volume variant (e.g. 747-100),  
   **I want** that variant's incidents on its own page when there are enough to be meaningful,  
   **so that** I'm not forced into an enormous undifferentiated 747 list.

3. **As a** product owner,  
   **I want** a reviewable mapping from 279 NTSB strings → catalog aircraft before any DB writes,  
   **so that** I control granularity and Stearman/helicopter scope.

4. **As a** developer,  
   **I want** import to fail closed on unmapped strings,  
   **so that** we never silently auto-create duplicate aircraft.

### FR-15: Family rollup proposal (product review) — **NEW**

1. **FR-15.1** Produce **`Planning/reviews/ntsb-family-rollup-proposal.md`** (or equivalent) that lists each distinct NTSB string with a **recommended** mapping action:
   - `map_to_existing` — attach to existing v3 `aircraft_id` (include target `model_name`)
   - `keep_variant` — keep variant-level page (existing or already in catalog)
   - `create_approved` — new catalog row explicitly approved (Stearman/helicopter families)
   - `skip` — do not import (out of portfolio scope)
2. **FR-15.2** Rollup rules (defaults — product may override per row):
   - **High-volume variant:** if a single NTSB string (or normalized variant key) has **≥ 10 incidents** in the 657 set, prefer **variant-level** page over generic family rollup.
   - **Low-volume suffix variants:** strings that differ only by customer suffix (`737-7H4`, `737-347`) roll up to nearest catalog family unless incident count alone justifies a page.
   - **Casing/spacing duplicates:** `BOEING 737` and `Boeing 737` must map to the **same** `aircraft_id`.
   - **Stearman / PT-17 cluster:** `BOEING A75N1(PT17)`, `BOEING B75N1`, `BOEING A75N1`, `BOEING E75` — map to **one** approved Stearman page (product decision 2026-05-31).
   - **Helicopters:** Create **new** helicopter catalog rows; page name **must include `Boeing` or `Airbus`** (e.g. `Airbus Helicopters AS350`, not bare `AS350`) (product decision 2026-05-31).
3. **FR-15.3** Target outcome: collapse **279 strings → ~15–30 approved canonical targets** (mostly existing catalog `aircraft_id`s; explicit `create_approved` only where product signs off).
4. **FR-15.4** **Review gate:** Product approves proposal before mapping file is finalized (Phase 5.15).

### FR-16: Canonical pre-import mapping file (JSONL gate) — **NEW**

1. **FR-16.1** Approved mapping lives at `data/config/ntsb_make_model_to_aircraft.jsonl` (path configurable; **committed to repo** after product approval).
2. **FR-16.2** Each line:
   ```json
   {
     "ntsb_make_model": "Boeing 757",
     "canonical_aircraft_id": 42,
     "canonical_model_name": "Boeing 757-200",
     "action": "map_to_existing",
     "notes": "optional"
   ```

4. **FR-16.4** One NTSB string → exactly one target; many NTSB strings may → same `aircraft_id`.
5. **FR-16.5** Version header comment line `# ntsb_make_model_to_aircraft v1 approved YYYY-MM-DD` at top of file.


### Rollup decision matrix (default)

| Condition | Default action |
|-----------|----------------|
| ≥ 10 incidents, single distinct string | `keep_variant` or map to existing variant page |
| < 10 incidents, customer suffix variant | Roll up to catalog family |
| Same family, different casing (`BOEING 737` / `Boeing 737`) | Same `aircraft_id` |
| Stearman PT-17 cluster | **One** Stearman page (`create_approved`) |
| Helicopter in Boeing/Airbus scope | **Create new** rows; name must contain **Boeing** or **Airbus** |
| Non-Boeing/Airbus or out-of-scope | `skip` |

Product may override any row in the proposal doc.
